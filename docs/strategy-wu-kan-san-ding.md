# promptdiff_32 战略分析：五看三定

> 分析方法：华为「五看三定」——先通过看行业/趋势、市场/客户、竞争、自己、机会洞察战略机会点，再通过定战略控制点、定目标、定策略形成可落地的规划。
>
> **重要前提**：`promptdiff_32` 目前是一个个人维护的开源项目，不是一家公司。因此本文的分析对象是「一个开源项目如何在既有生态中找到不可替代的位置」，而不是「一个创业公司如何融资扩张」。任何把它当成商业计划书来读的预期，都会导致错误结论——包括对我自己。
>
> 数据时点：2026 年 10 月。文中引用的行业数据来自公开报道，标注了来源，但**未做一手核实**，用于判断方向而非精确测算。

---

# 第一部分：五看

## 一、看行业/趋势

### 1.1 三个不可逆的行业事实

**事实一：LLM 应用的故障模式变了，但质量保障手段没跟上。**

传统软件的 bug 是确定性的：同样输入必然同样输出，所以单元测试能覆盖。LLM 应用的输出是概率性的，同一个 prompt 两次调用可能给出不同措辞，甚至不同的承诺口径。这让「回归测试」这件在软件工程里已经解决了几十年的事，突然失效了。

行业数据侧面印证了这个缺口：LangChain 的一项调查显示，89% 的受访者已经部署了可观测性，但 **52.4% 只做离线评估，29.5% 完全没有任何评估机制**（转引自公开报道，2026）。也就是说，「看得到」（可观测）和「管得住」（回归门禁）之间有一道很宽的沟。

**事实二：模型迭代速度已经超过人工验证速度。**

模型厂商的版本节奏是月级甚至周级。每次模型升级，企业面临同一个问题：**我该不该跟？** 没有基线对比，答案只能靠抽样目测。这是 promptdiff_32 直接命中场景。

**事实三：评估正在从「研究行为」变成「工程行为」。**

2024–2025 年，评估工具的主要用户是算法团队，产出物是论文式的评测报告。2026 年的趋势是它进入研发流程：谁改的、改了什么、影响了哪几条用例、能不能合。这个转变对工具的要求完全不同——**工程化要求确定性、可重复、可进 CI，而不是要求指标先进**。

### 1.2 趋势判断

| 趋势 | 方向 | 对本项目的含义 |
| --- | --- | --- |
| 评估工具工程化 | 从「跑分」到「门禁」 | ✅ 正面。本项目的定位正在这条线上 |
| 平台化整合 | 评测被并入可观测性平台（LangSmith、Braintrust、Arize、Langfuse） | ⚠️ 中性偏负。独立小工具容易被「顺便做了」 |
| 模型厂商收编评测能力 | Promptfoo 于 2026 年 3 月被 OpenAI 宣布收购，技术将并入其 Agent 平台 | ✅ 强正面。中立性出现空位 |
| 合规压力上升 | AI 治理要求「可证明的测试记录」 | ✅ 正面。回归记录天然是合规证据 |
| Agent 化 | 评估对象从单轮问答转向多步任务 | ⚠️ 负。本项目的单轮假设会被挑战 |

**趋势层面的核心结论**：行业在往「工程化 + 平台化」两头走。中间地带——**轻量、可嵌入、厂商中立**——反而因为巨头收编而空了出来。这是本项目唯一值得押注的位置。

## 二、看市场/客户

### 2.1 谁真的痛

按痛感强度排序（这是本分析最关键的排序，直接决定后续所有取舍）：

| 客户类型 | 具体痛点 | 痛感 | 付费意愿 | 是否本项目目标 |
| --- | --- | --- | --- | --- |
| **中小 AI 应用团队（5–50 人）** | 改 prompt 靠感觉，上线靠运气，出事靠客户投诉 | 强 | 低（预算在模型调用上） | ✅ 主目标 |
| 独立开发者 / 小团队 | 一个人维护多个 AI 功能，没有精力做评测 | 中强 | 无 | ✅ 主目标 |
| 大企业 AI 中台 | 有预算买平台，但要求私有化、可审计 | 强 | 高 | ❌ 不是（销售成本远超能力） |
| 模型厂商 | 需要对外证明模型能力 | 强 | 高 | ❌ 不是（会被要求做定制） |
| 学术研究 | 需要榜单与指标 | 中 | 无 | ❌ 不是（指标哲学不同） |

### 2.2 客户的真实工作流

一个 10 人 AI 团队改一次提示词的现实流程：

```
产品提需求 → 工程师改 prompt → 自己试几条 → 感觉可以 → 上线 → 观察两天 → 出事/没事
```

中间缺失的环节是「**这次改动影响了什么**」。注意：他们缺的不是「评估能力」（他们知道什么叫好答案），缺的是**把判断固化成可重复执行的东西**。

这决定了一个反直觉的产品要求：**工具的第一次使用必须足够便宜**。如果为了跑回归要先写 200 条用例、配一套标注流程、接一个平台账号，那它一定不会被用起来。**能跑起来的 8 条用例，胜过躺在文档里的 200 条。**

### 2.3 市场规模的诚实判断

第三方口径称 LLM 可观测性与评估市场 2026 年约 26.9 亿美元、2030 年约 92.6 亿美元（CAGR 约 36%）。这个数字对本项目**几乎没有意义**——它不是可服务市场。

真正相关的是「愿意在 CI 里装一个开源回归工具的中小团队数量」。这个数无法获得，只能用一个可观测的代理指标估计：**GitHub 上同类工具（promptfoo）的 star 与 issue 活跃度**。它们的规模是万级 star，说明需求真实存在，但已经被满足了一部分。本项目的现实目标不是抢存量，而是**接住那些因为「太重/要联网/要账号/不信任厂商」而放弃的人**。

## 三、看竞争

### 3.1 竞品地图

| 工具 | 定位 | 形态 | 优势 | 对本项目的威胁 |
| --- | --- | --- | --- | --- |
| **promptfoo** | prompt/模型测试 + 红队 | Node CLI + Web UI | 生态成熟、多模型横向对比、红队能力、CI 集成 | 🔴 极高，几乎覆盖本项目全部功能 |
| **DeepEval** | pytest 风格的 LLM 评估 | Python 库 | 20+ 指标、原生 CI、社区大 | 🟠 高，Python 生态内的直接替代 |
| **LangSmith / Braintrust / Arize / Langfuse** | 可观测 + 评估平台 | SaaS（部分可自托管） | 端到端、可视化、团队协作 | 🟡 中，重、需接入、数据出域 |
| **Ragas** | RAG 专项指标 | Python 库 | RAG 场景指标专业 | 🟢 低，场景不同 |
| **lm-evaluation-harness / OpenCompass** | 模型能力榜单 | 研究工具 | 学术权威 | 🟢 低，目标不同 |
| **自研脚本**（`assert "退款" in resp`） | 项目内临时校验 | 脚本 | 零成本、完全可控 | 🔴 极高，是最大的「竞品」 |

**最被低估的竞争者不是 promptfoo，而是「工程师自己写的 30 行 Python 脚本」。** 任何新工具的默认对手都是「什么都不装」。

### 3.2 Promptfoo 被 OpenAI 收购意味着什么

这是 2026 年这个赛道最重要的一件事：**最主流的开源评测工具被模型厂商收编了**。

含义有三层：

1. **功能层面**：promptfoo 会更深入地绑定 OpenAI 的 Agent 平台，非 OpenAI 模型的对比体验可能不再是第一优先级（官方声明将保持独立运营并继续维护开源项目，但激励结构已经改变）。
2. **信任层面**：当你的评测工具由被评测方提供，中立性就成了结构性问题。对需要跨模型选型的团队来说，这是真实顾虑。
3. **生态层面**：一个空位出现了——**「不属于任何模型厂商」的评测工具**。

这不是说 promptfoo 会变差，而是说**它不再是唯一合理的选择**。对一个小项目来说，这已经是难得的窗口。

### 3.3 竞争结论

本项目在功能维度上**不可能赢**，也不需要赢。可行的竞争方式是**换维度**：

| 维度 | 大平台 | promptfoo / DeepEval | promptdiff_32 的机会 |
| --- | --- | --- | --- |
| 功能广度 | 强 | 强 | 放弃 |
| 部署成本 | 需接入/账号 | 需 Node/Python 生态 + 依赖 | ✅ 零依赖，单命令 |
| 厂商中立 | 弱 | 中（正在变化） | ✅ 强 |
| 数据出域 | 是 | 部分 | ✅ 完全本地 |
| 长期可运行性 | 依赖服务存续 | 依赖依赖树 | ✅ 只用标准库 |
| 中文场景适配 | 弱 | 弱 | ✅ 强 |

## 四、看自己

### 4.1 资源盘点（诚实版）

| 项 | 现状 | 评价 |
| --- | --- | --- |
| 人力 | 1 人，业余时间 | 🔴 最大约束 |
| 资金 | 0 | 🔴 无法做市场、无法买流量 |
| 技术能力 | 能独立完成核心功能与测试 | 🟢 够用 |
| 时间持续性 | 无保障，可能中断 | 🔴 开源项目死亡率最高的原因 |
| 已有资产 | 50 个测试、完整文档、可运行 demo、真实分支历史 | 🟢 起点比多数个人项目高 |
| 渠道 | 无 | 🔴 冷启动只能靠内容与社区 |

### 4.2 能力上的真实优势

不是「我写得更好」，而是三个结构性选择带来的优势：

1. **零第三方依赖**。这不只是技术洁癖，它是**部署确定性的承诺**：三年后仍能跑起来，CI 镜像不用为它加层，安全审计不用审依赖树。在大平台靠功能碾压的环境里，这是唯一无法被快速复制的属性（因为复制它意味着放弃自己生态的优势）。
2. **代码量小到可读完**。核心 7 个模块、约 1200 行。用户可以在一小时内读完全部实现，这对「要放进自己 CI 的关键路径」的工具是硬要求。
3. **中文语境的一等公民**。断言匹配忽略空白但保留标点、文档全中文、issue 模板中文——这些细节国际工具不会做。

### 4.3 真实短板（不粉饰）

| 短板 | 后果 | 缓解方式 |
| --- | --- | --- |
| 功能远少于 promptfoo | 有复杂需求的用户直接走 | 明确「只做回归门禁」，不试图覆盖 |
| 单维护者 | 一次长期中断即项目死亡 | 文档完备 + 测试充分 + 核心逻辑极简，降低接管门槛 |
| 无 LLM-as-judge 指标 | 无法评估「回答质量好不好」 | 明确边界：本工具管「有没有变」，不管「好不好」 |
| 单轮对话假设 | Agent 场景不适用 | 写进 README 的已知限制，不假装支持 |
| 无社区 | 无 issue、无 PR、无传播 | 先做内容（分析、教程），再谈社区 |
| 英文文档缺失 | 国际传播受限 | 双语文档列为 v1.0 目标 |

### 4.4 SWOT

| | 有利 | 不利 |
| --- | --- | --- |
| **内部** | **S**：零依赖、极简、厂商中立、中文友好、文档与测试完备 | **W**：单维护者、功能窄、无社区、无英文文档 |
| **外部** | **O**：Promptfoo 被收编留下中立空位；52.4% 团队只做离线评估；合规要求可证明的测试记录 | **T**：平台把评测做成免费功能；模型厂商自带 eval；工程师自研脚本的惯性 |

**SWOT 的交叉结论（这是全篇最重要的一句）**：

> 用 **S × O** 切入：以「厂商中立 + 零依赖 + CI 原生」去接住 Promptfoo 被收编后流失的、对中立性敏感的中小团队。
> 同时用 **W 对冲 T**：因为功能窄，所以不与平台正面竞争；因为极简，所以平台「顺便做了」也替代不了「拷一个文件就能跑」的确定性。

## 五、看机会

### 5.1 机会点收敛

从上面四看收敛出三个候选机会点，逐一筛：

| 候选机会 | 判断 | 理由 |
| --- | --- | --- |
| A. 做「轻量中立版 promptfoo」 | ❌ 放弃 | 功能军备竞赛，1 人必输；且 promptfoo 已开源，无壁垒 |
| B. 做「LLM 应用的回归门禁标准」 | ✅ **选择** | 场景窄、边界清晰、可被 CI 直接消费、与大平台互补 |
| C. 做「AI 合规测试记录工具」 | ⏸ 暂缓 | 需求真实但销售驱动，个人项目无法获客；可作为 B 的延伸叙事 |

### 5.2 机会点的具体形状

**机会 = 中小 AI 团队在「改完 prompt 到上线」之间的 30 分钟。**

这 30 分钟里他们的行为是：翻聊天记录找之前试过的例子、手动跑几条、凭感觉判断、上线。如果有人能让他们在这个位置执行一条命令就得到「哪几条变坏了」，价值就成立。

这个场景的三个特征是设计约束，不是营销话术：

1. **必须能在 5 分钟内跑起来** → 零依赖、单命令、内置示例；
2. **必须不引入新的信任成本** → 不联网、不要账号、代码可读；
3. **必须能直接进 CI** → 退出码、JSON 输出、报告文件。

# 第二部分：三定

## 六、定战略控制点

### 6.1 什么是控制点

战略控制点是「即使对手看见了、也难复制或不愿复制」的东西。常见的控制点类型：标准/专利、客户关系、数据飞轮、生态锁定、成本结构、品牌。

### 6.2 候选评估

| 控制点类型 | 本项目是否可行 | 判断 |
| --- | --- | --- |
| 数据飞轮 | ❌ | 本地工具，不收集数据，也不该收集 |
| 生态锁定 | ❌ | 零依赖本身反对锁定 |
| 专利/标准 | ❌ | 个人项目无力推动标准 |
| 品牌 | ⚠️ 长期 | 只能靠持续输出内容积累，慢 |
| **切换成本（组织流程嵌入）** | ✅ | 一旦进入 CI 流水线，替换需要改流程 |
| **技术独特性（零依赖 + 可读性）** | ✅ | 对手复制它等于放弃自身优势 |

### 6.3 结论：控制点选「流程嵌入 + 部署确定性」

```
战略控制点 = 进入 CI 流水线（切换成本）
           × 零依赖带来的部署确定性（对手不愿复制）
           × 厂商中立（对手结构上做不到）
```

三条缺一不可，且**乘号不是加号**——任何一条为零，控制点就归零。

诚实评价：**这是一个弱控制点。** 它能带来的最好结果是「被稳定使用」，而不是「不可替代」。因此策略上必须放弃「防守」，转向「持续降低使用门槛 + 持续输出内容」。这也是为什么下面的目标里没有「star 数」这类虚荣指标。

## 七、定目标

### 7.1 北极星指标

**每周被真实项目在 CI 中调用的运行次数。**

无法直接观测（不收集遥测，这是刻意放弃的），因此用三个代理指标合成：

| 代理指标 | 观测方式 | 说明 |
| --- | --- | --- |
| PyPI 下载量 | 公开统计 | 反映安装规模，噪声大（CI 重复拉取） |
| Docker 镜像拉取 | 若提供镜像 | 更接近「流水线使用」 |
| issue / discussion 中出现的真实用法 | 人工统计 | 最高质量信号，量小但真 |

### 7.2 分层目标

| 时间 | 目标 | 验证方式 | 是否核心 |
| --- | --- | --- | --- |
| **3 个月** | 有 3 个外部项目在 CI 中实际使用 | issue/README 中可见的用法 | ✅ |
| **3 个月** | 零 P1 缺陷存续，CI 全绿 | Actions 记录 | ✅ |
| **6 个月** | v1.0：CLI 与 JSON schema 承诺向后兼容 | 发布说明 | ✅ |
| **6 个月** | 中英双语文档完备 | 仓库结构 | ✅ |
| **6 个月** | 累计 50 star | GitHub | ❌ 虚荣指标，仅记录 |
| **12 个月** | 进入 1 个以上「LLM 评测工具」清单类仓库 | 被收录 | ✅ |
| **12 个月** | 至少有 1 位外部贡献者合并过 PR | git log | ✅ |
| **12 个月** | 沉淀 3 个真实回归案例（脱敏后写入文档） | docs/cases | ✅ |

**为什么 star 不是核心指标**：star 与「是否被使用」的相关性在工具类项目里很弱。一个 2000 star 的评测工具可能没有一个用户在 CI 里跑它。用 star 做目标会诱导做「看起来很酷的 demo」，而不是「跑得稳的门禁」。

### 7.3 反目标（明确不追求的）

- 不做用户增长运营（不刷 star、不做抽奖式推广）；
- 不做功能对标（不追 promptfoo 的功能列表）；
- 不做商业化验证（现阶段不以变现为目标）。

## 八、定策略

### 8.1 产品策略：窄化到极致

**只做一件事：判断「这次改动有没有让已有用例变坏」。**

具体约束（写进代码与文档，不只是口号）：

| 约束 | 具体做法 |
| --- | --- |
| 不做 LLM-as-judge | 不引入「用模型评模型」，因为不确定性与成本会破坏 CI 的确定性 |
| 不做多轮对话（v0.x） | 单轮假设写进已知限制，宁可窄也不假装支持 |
| 不做标注/看板 | 报告只输出 Markdown 与 JSON，可视化交给下游 |
| 断言只做确定性匹配 | contains / not_contains / 延迟，三类足够覆盖 80% 的门禁需求 |
| 保留「漂移」而不只是「通过/失败」 | 因为真实的回归往往先表现为措辞变化 |

### 8.2 技术策略：把「简单」做成壁垒

1. **零运行时依赖**写进 CONTRIBUTING，作为不可协商项。新增依赖需要 issue 讨论——这条规则本身就是护城河。
2. **核心代码不超过 1500 行**。超过就说明范围失控，需要拆或砍。
3. **JSON schema 只增不删**。基线文件是用户资产，破坏兼容等于让用户的基线和历史失效。
4. **确定性优先于精度**。相似度用 difflib 而非向量模型：同一输入永远同一分数，这是 CI 工具的第一要求。
5. **测试覆盖「错误路径」而不只是「正确路径」**。已有的 57 个测试里，一半以上在验证非法输入、接口报错、空集合这类情况。

### 8.3 社区策略：降低参与门槛，而不是扩大声量

| 动作 | 目的 |
| --- | --- |
| issue 模板强制填「复现步骤 + 用例片段」 | 减少往返，让外部 issue 可直接变成测试用例 |
| 标注 `good first issue`，限定在文档与测试 | 让新人第一次 PR 就能成功 |
| CONTRIBUTING 里写清「新增断言要改哪四处」 | 降低结构性改动的心智成本 |
| 双语文档（v1.0 目标） | 突破中文圈传播上限 |
| 每季度一篇「真实回归案例」 | 内容即获客，比推广更持久 |

### 8.4 合规与信任策略

- **不收集任何遥测**，写进 SECURITY.md 作为承诺；
- API key 只从环境变量读取，不落盘（已有实现 + 测试）；
- 用例集与基线可能含业务敏感信息，明确「脱敏是使用者责任」，并在文档里给出脱敏建议；
- 把「回归记录可作为合规证据」作为长期叙事，但不做合规认证类承诺。

### 8.5 明确不做的事（战略放弃清单）

放弃比选择更能说明战略。以下项目**明确不做**，且会在 README 与 issue 回复中引用本节：

| 不做 | 原因 |
| --- | --- |
| SaaS 版本 / 云托管 | 与「数据不出本地」的核心承诺冲突 |
| 多模型 A/B 平台化 | 已列入路线图但只做 CLI 级对照，不做看板 |
| 自动改 prompt（AI 优化） | 把工具从「裁判」变成「选手」，破坏中立性 |
| 模型托管 / 网关 | 完全不同的问题域 |
| 支持所有评估指标 | 指标军备竞赛，1 人必输 |

## 十、关键假设与风险

战略的脆弱处往往在假设里，所以单独列出，并给出**可被证伪的验证方式**。

| 假设 | 如果不成立会怎样 | 如何尽早验证 |
| --- | --- | --- |
| 中小团队愿意手写 JSON 用例 | 工具无人使用，因为「写用例」本身就是门槛 | 观察 issue 里是否有人贴出自己的用例集；提供「从日志生成用例」的能力作为兜底 |
| 「零依赖」是真实卖点而非自嗨 | 差异化消失，退化为「promptfoo 的残缺替代」 | 在 README 里把它作为首要卖点，看是否带来 star/使用转化 |
| 中立性会被用户在决策中实际考虑 | 收编事件带来的窗口被浪费 | 在 discussion 中直接问「你选评测工具时是否在意厂商归属」 |
| 单维护者能持续投入 12 个月 | 项目停滞，用户流失 | 用「文档完备 + 核心极简」降低中断损失；每季度发布一次 |
| CI 门禁是真实需求而非伪需求 | 定位错误，需要重做市场判断 | 统计「用了 `--fail-on-regression` 的 issue 数量」 |

**最大的风险不是竞争，而是「需求被高估」**——即工程师其实并不觉得提示词回归值得专门装一个工具。这一点必须在 3 个月内用真实使用数据证伪或证实，否则后续所有投入都建立在沙上。

## 十一、复盘机制

| 频率 | 看什么 | 决策 |
| --- | --- | --- |
| 每月 | 代理指标（下载量、issue 用法数） | 是否需要调整传播方式 |

## 附：一页纸结论

- **行业**：评估从研究走向工程，平台化与厂商收编同时发生，中立空位出现。
- **市场**：中小 AI 团队痛在「改完 prompt 不知道影响了什么」，且预算极低、耐心极短。
- **竞争**：功能上必输，只能换维度（部署成本、中立性、可读性）；最大对手是「自研 30 行脚本」。
- **自己**：优势是零依赖与极简，短板是单人与无渠道，必须靠窄化生存。
- **机会**：做「改完 prompt 到上线之间的 30 分钟」的回归门禁，不做平台。
- **控制点**：CI 流程嵌入 × 部署确定性 × 厂商中立，弱但唯一可行。
- **目标**：以「被真实 CI 调用」为北极星，star 只记录不追求。
- **策略**：产品窄化、技术极简、社区低门槛、合规不遥测；明确列出不做清单。
- **最大风险**：需求被高估。3 个月内必须用真实使用数据验证。
